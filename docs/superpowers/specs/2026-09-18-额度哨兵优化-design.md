# 额度哨兵 UI 与数据链路优化设计

**版本：** v1
**日期：** 2026-09-18
**状态：** 待用户审阅
**范围：** 保持无登录、无数据库、Git 唯一数据源；优化前端 UI、移动/桌面响应式、可访问性、订阅入口和轮询可靠性。

## 1. 目标与成功标准

本轮目标不是复制 resetrelay.com，而是让“额度哨兵”在 3 秒内回答三个问题：

1. 当前雷达是否在线，距离下一次扫描还有多久？
2. 最近一次重置是什么时候，未来 24 小时的趋势参考是什么？
3. 用户如何订阅提醒、验证数据来源？

成功标准：

- 375px、430px、1440px 视口均无横向溢出；桌面端利用更宽空间呈现 Hero 和统计信息。
- 页面有一个 `h1`、分区有明确 `h2`，所有交互控件可通过键盘操作且有可见焦点。
- 动态流的“全部”确实包含普通动态；默认只展示最近 6 条，用户可展开其余记录。
- 订阅入口有可用/缺失两种状态；二维码缺失时不会把占位内容伪装成可用订阅。
- 轮询对远端数据先校验再通知；已经记录为 `sent` 的事件 ID 不会因为正常重跑重复推送；失败状态能写入健康文件并触发运维告警。
- `pnpm test`、`pnpm validate`、`pnpm build` 和浏览器桌面/移动走查通过。

## 2. 不变约束

- 不增加账户体系、登录、数据库或用户个人数据存储。
- Git 仓库中的 `data/events.json` 仍是历史事件唯一持久来源。
- 不抓取私有内容，不绕过上游访问限制；每条记录保留 X 原帖链接。
- 继续使用飞书群机器人作为订阅和运维通知渠道。

## 3. 前端设计

### 3.1 信息架构

页面结构保持单页，但调整为：

1. `header`：产品名、简短价值说明、上游作者链接。
2. `h1` Hero：在线状态、等待天数、倒计时/雷达、24 小时概率、最近一次信号摘要和两个 CTA。
3. `section#history`：统计卡与 26 周历史网格。
4. `section#feed`：最近动态，展示已核验数量和更新时间。
5. `section#subscribe`：飞书订阅弹层触发器、RSS 备用入口、无登录说明。
6. `footer`：数据口径、更新时间、免责声明与上游来源。

### 3.2 响应式布局

- 桌面（`min-width: 900px`）：主容器 1100–1180px；Hero 采用左侧倒计时/雷达、右侧概率卡的两列布局；统计卡为三列；动态列表为宽卡片，时间列独立对齐。
- 平板（`600–899px`）：Hero 改为上下两行，统计卡仍保持两列或三列自适应。
- 手机（`<600px`）：Hero、概率卡、最近信号全部堆叠；统计卡单列；历史网格保持紧凑但不产生滚动溢出；动态默认显示 6 条，使用“显示更多”按钮。
- 所有断点使用 CSS class 和 token，避免继续依赖大量组件内联 style。

### 3.3 视觉与交互

- 保留深色荧光绿主题，但提高正文和辅助文字的对比度，减少低对比度的装饰文本。
- 统一卡片、按钮、徽章、焦点环和状态颜色；危险/降级状态使用琥珀色，不只依赖颜色表达。
- 为动画加入 `@media (prefers-reduced-motion: reduce)`，禁用雷达扫动和脉冲动画。
- Hero 的概率环、倒计时和在线徽章提供可读的文本标签；历史网格每个有事件的单元格提供 `aria-label` 或可访问说明。
- 动态列表的过滤按钮使用 `aria-pressed`；展开按钮使用 `aria-expanded` 并在状态变化后保持焦点。

### 3.4 订阅状态

- 新增客户端订阅弹层组件：有二维码资源时展示二维码、订阅说明和关闭按钮；没有二维码时展示“订阅入口尚未配置”，同时提供 RSS 链接。
- 订阅弹层支持 Escape 关闭、背景点击关闭、打开时聚焦关闭按钮。
- 不采集表单、不写入服务器、不声称完成了订阅。

## 4. 数据与后端设计

### 4.1 健康状态

将 `data/health.json` 扩展为兼容旧格式的结构：

```json
{
  "lastSuccessAt": "2026-09-18T02:00:00.000Z",
  "lastFailureAt": null,
  "lastError": null
}
```

页面继续根据 `lastSuccessAt` 判定在线，同时在降级状态中提供最近失败时间/简短原因（不泄露 secret）。

### 4.2 轮询幂等与校验

轮询顺序调整为：

1. 拉取远端数据。
2. 对所有远端候选事件做字段、时间、原帖 URL 和类型校验。
3. 按 `tweet_id` 与本地事件集合 diff。
4. 对新事件先按事件 ID 检查是否已有成功推送记录；未推送的才进入通知。
5. 通知成功后写入事件和推送状态；写盘前再次运行 schema 校验。
6. 任一步失败，保留已成功写入的数据、更新健康失败字段，并在满足阈值时发送运维告警。

为避免引入数据库，推送状态使用仓库内 `data/deliveries.json`（事件 ID、目标、状态、时间、重试次数）作为轻量幂等日志；该文件只记录事件元数据，不保存用户信息和 webhook。正常重跑按 `sent` 状态跳过重复通知；若进程在 webhook 成功后、写入 `sent` 之前崩溃，仍存在一次性重复通知窗口，下一轮会优先告警并继续恢复，不宣称外部 webhook 的严格 exactly-once。

### 4.3 workflow 与 RSS

- GitHub Actions 保留 30 分钟调度，增加明确的并发取消/等待策略，避免两个轮询同时推送。
- 提交步骤只提交数据文件和必要日志；无变化时不产生无意义 commit。
- RSS 的站点 URL 改为环境变量/配置项，开发环境使用本地默认值，生产环境不再输出 placeholder 域名。
- CI 增加 `pnpm test` 对 RSS 输出、health 兼容读取、delivery 幂等和非法远端事件的覆盖。

## 6. 验证计划

1. 单元测试：schema、health、delivery 幂等、RSS、FeedList 展开/筛选逻辑。
2. 静态检查：`pnpm validate`、`pnpm test`、`pnpm build`。
3. 浏览器走查：375px、430px、1440px；检查横向溢出、焦点、Escape 关闭弹层、筛选/展开、祈愿计数和降级文案。
4. 手工后端检查：`pnpm poll -- --dry-run`，确认无新事件时不发送、不写 delivery；构造已 `sent` 的重复事件确认会跳过通知，并验证 webhook 成功后进程中断时的恢复/告警行为。

## 7. 风险与降级

- 二维码仍未配置：页面继续可用，订阅区域明确显示未配置，并提供 RSS。
- 上游接口不可用：保留最近一次 Git 快照，页面显示降级；不清空历史数据。
- 飞书 webhook 失败：不丢事件，delivery 保持 pending/failed，下一轮重试并告警。
- GitHub Actions 或部署失败：数据仍留在工作区/下一轮 diff 可恢复；不静默把失败标记为成功。
